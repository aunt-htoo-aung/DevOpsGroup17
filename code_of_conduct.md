# Group 17 Code Of Conduct

## 1. Purpose, Scope & Professional Ethics

This Code of Conduct sets out the explicit expectations, standards, values, and operating procedures that all six members of the project team agree to uphold throughout the lifecycle of the **SET09803 DevOps coursework**. It applies equally to every team member regardless of role, ensuring complete fairness, transparency, and mutual respect.

* **Professional and Respectful Collaboration:** All members are expected to interact professionally, listen actively to differing viewpoints, encourage constructive feedback, and resolve technical or operational disagreements calmly and fairly. Maintaining a supportive atmosphere is paramount to team productivity.
* **Proactive Communication:** Members must communicate potential blockers or delays early to allow the team to adjust sprint plans without penalty.

---

## 2. Team Roles, Work Distribution & Definition of Done

To ensure efficient execution of the **32 system requirements** and **DevOps infrastructure tasks**, responsibilities are structured around Scrum roles and clear work distribution standards.

### Scrum Roles & Responsibilities

* **Product Owner:** Defines and communicates the product vision, sets backlog priorities in Zube.io, validates user stories against assignment specs, and ensures business/academic alignment.
* **Scrum Master:** Facilitates fair communication, mediates team conflicts, enforces GitFlow standards, manages Sprint/Kanban boards, and ensures everyone's contributions are valued.
* **Development / DevOps Team Members:** Follow this Code of Conduct at all times, complete assigned tasks within sprint deadlines, write clean Java/SQL code with unit tests, and report blockers immediately.

### Fair Work Distribution
Tasks are allocated fairly considering each member's skills, workload, and availability. Members are encouraged to contribute equally across all phases (**DevOps pipeline, Java backend, SQL database, and documentation**) so that no single individual is overburdened.

### Definition of Done (DoD)
A task or User Story is strictly considered **'Done'** ONLY when:

1. It has been fully implemented and unit tested.
2. A Pull Request from the member's feature branch/fork to `develop` has been opened.
3. Automated GitHub Actions CI builds pass.
4. The code and task have been fully reviewed and approved by the Scrum Master / Peer reviewer.

*This shared definition guarantees consistent quality across all project deliverables.*

## 4. Core Operational Rules and GitFlow Standards

* **GitFlow Discipline:** Direct commits to the `master` or `develop` branch are strictly prohibited. All work must be carried out on dedicated feature branches and merged exclusively via reviewed Pull Requests (PRs).
* **Task Management & Planning:** All work must be tracked via Product Backlog items, User Stories, and Sprint/Kanban boards integrated with Zube.io (or similar tool) and GitHub Issues.
* **Continuous Communication:** Team members must check primary communication channels daily and respond to project-related inquiries within 24 hours.
* **Code Quality & Documentation:** All pushed code must be clean, commented, and build cleanly through Maven and Docker pipelines on GitHub Actions.

---

## 5. Progressive Disciplinary Ladder & Penalty Matrix

To maintain accountability while fostering a supportive environment, the team implements a four-stage progressive disciplinary framework combining educational reminders, symbolic fines, and formal contribution deductions.

* **Stage 1 — Friendly Reminder:** A gentle verbal or text notification for minor, first-time, or unintentional mistakes (e.g., slightly late submission, minor commit omission).
* **Stage 2 — Friendly Fine:** Symbolic accountability penalties applied in a lighthearted but fair way for recurring minor issues (e.g., bringing snacks/drinks to next physical meeting, preparing extra presentation slides, taking an additional minor supporting task).
* **Stage 3 — Contribution Deductions (Moodle Individual Contribution Spreadsheet):** For unaddressed violations, mark deductions will be applied directly to the agreed Individual Contribution Spreadsheet (100% team total) as follows:

### Penalty Matrix

| Offense / Breach | Deduction Rate | Operational Notes & Conditions |
| :--- | :--- | :--- |
| **Meeting Lateness** | `-0.1 pts` / instance | Arriving > 5 mins late to scheduled group or Code Review meetings without prior notice. |
| **Unexcused Absence** | `-0.5 pts` / instance | Missing a scheduled meeting completely without advance notification or valid mitigation. |
| **Communication Failure** | `-0.2 pts` / day | Failing to respond to team inquiries or project updates for over 24 hours without notice. |
| **Incomplete Sprint Task** | `-1.0 pts` / task | Failing to deliver assigned User Stories or tasks within the agreed Sprint deadline. |
| **Zero GitHub Activity** | `-1.5 pts` / week | A full week without commits, PR creations, or issue updates logged on GitHub. |
| **Absence Code Review Session** | `-3.0 pts` / session | No warning stage; direct mark deduction applied for missing this session. |
